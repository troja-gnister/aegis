## Bottleneck evidence

Measured: 40.38 requests/s; web 40.59 ms and PostgreSQL 46.46 ms of CPU per request; concurrent list p50 is 4.38x the sequential p50. Sequential single-user p50 (ms): list 52.4, details 50.6, status 53.2.

- inferred: concurrent list p50 is 4.38x the sequential service time, so most loaded latency is waiting for a shared resource rather than per-query work
- inferred: web averaged 163.9% of one core, above one core, so request work is not purely serialized by one Python GIL (C extensions release it); the single-process hypothesis is only partly supported
- inferred: PostgreSQL used at least as much CPU as web (187.6% vs 163.9% of one core). With no persistent connections, every request opens a new database connection (backend start and SCRAM login) plus a locking transaction; that is a plausible major cost, not profiled here
